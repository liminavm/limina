# The first run's "committed MTL4CommandBuffers are never deallocated (0/96, 0/384); the queue
# retains them" was the PROBE'S OWN BUG, not Metal behavior: encode_pass did
# [[g_dev newCommandBuffer] retain] — `new` already returns +1, so every cb carried a leaked
# extra reference and could never die. The internal proof was already in the record: the
# flush_roundtrip cbs go through the probe's full release path and are NOT in the sentinel
# denominators, so a balanced probe must read dead_cbs >= 2 in EVERY mode — it read 0
# everywhere, including MODE=c where nothing else was released.
# Fix: drop the extra retain; add report_sentinels after queue release (the first run inferred
# "the queue retains them" from a footprint delta alone and never sentinel-tested it).
# Consequences confirmed by rerun below:
#   - cbs dealloc PROMPTLY on release: 98/96 at "cbs released" (>96 = the flush cbs). The queue
#     retains NOTHING. Finding 3 of the first analysis is RETRACTED.
#   - MODE=a's staged teardown now genuinely stages, and attributes cleanly: releasing all 96
#     cbs (all dead) moves ioaccel by 0.0 MiB — the ALLOCATORS own every heap region.
#   - The MODE=d footprint creep was the leaked ObjC objects: now flat at +13.9 MiB after
#     cycle 1. The ~13 MiB residual is one-time process/driver state, not per-cb cost.
#   - After queue release: footprint +9.5 MiB, AGXResource +0. Clean.
# Headline verdicts unchanged: 100% return, MODE=a/b/d all reconfirm.
