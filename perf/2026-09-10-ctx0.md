# ctx0 fence sync: skipping it buys nothing measurable

**Question.** A classic (vrend) fence syncs every sub-context of its context *plus* ctx0. The
ctx0 sync costs an `eglMakeCurrent`, a synchronous flush and a reset of the bound-program cache
(`third_party/virglrs/src/vrend/vrend.rs`, the `VIRGLRS_FENCE_SKIP_CTX0` site). It was the lead
for the `vkmark-default-venus` drop in `2026-09-10-parkpresent.md`. virglrs `593350e` added
`VIRGLRS_FENCE_SKIP_CTX0=1` to drop it, for pricing only.

**Answer: no.** With the sync skipped, neither vkmark nor the renderer's own per-command cost
improved against the adjacent shipped-behaviour leg, in either pair. The ctx0 sync does not
explain the vkmark drop.

## Result

Enhanced guest, debug worker (renderer at `opt-level = 3`), limina `4eaec9a0`, virglrs `593350e`.
Legs in run order, one boot each, alternating so host drift cannot line up with the knob.

| leg | knob | vkmark (3 runs) | control before / after | median µs/cmd | cmd/s | fence/submit |
|---|---|---|---|---|---|---|
| 1 | unset | 4235 / 4251 / 4321 | — / 767 | 1.48 | 3675 | 1.50 |
| 2 | **skip** | 4275 / 4282 / 4337 | 775 / 784 | 1.52 | 3704 | 1.50 |
| 3 | unset | 3874 / 4035 / 3920 | 767 / 784 | 1.83 | 3617 | 1.50 |
| 4 | **skip** | 4053 / 3987 / 3994 | 778 / 784 | 1.95 | 3677 | 1.50 |

- **Read each skip leg against its neighbour, never against the other pair.** Legs 3-4 ran
  ~8% slower than 1-2 by *both* instruments, slow in every quarter of each run and across two
  separate boots — a sustained host state lasting tens of minutes. The llvmpipe control stayed
  in band throughout because it is CPU-bound in the guest and cannot see host-renderer speed.
  An A-A-B-B order would have reported that drift as the knob.
- **The workload was identical across all four legs** (cmd/s, batch/s, fence/s and 1.50
  fence/submit agree to ~2%), so a µs/cmd difference would be the renderer's cost, not a
  different stream.
- **vkmark exercises this path hard despite running on venus**: ~3700 vrend cmd/s and ~175
  fence/s while it runs, from the compositor's GL path. The instrument can respond to the
  treatment; this is not a confident null from a blind needle.
- **No knob-tracking climb.** Run-over-run increases appear on a shipped leg (1) and are absent
  on a skip leg (4).

## Controls

- **The knob is live in the code.** `a_fence_covers_every_sub_context_and_ctx0` passes with
  the knob unset (4 syncs) and fails with it set (`left: 3, right: 4`). The failing run then
  aborts on drop — the test's own `Fence` aborts undropped — which is not a second fault.
- **The environment reaches the renderer.** The supervisor never clears the worker's
  environment, and `VIRGLRS_SUBMIT_STATS=5`, set on all four legs, reported from each boot.
- **Host gate.** llvmpipe control 767-784 on every leg; a leg the user saw disturbed by host
  CPU activity was discarded and re-run (its first vkmark run read 3734).

## Method

`VIRGLRS_SUBMIT_STATS=5` on every leg; `VIRGLRS_FENCE_SKIP_CTX0=1` on legs 2 and 4 only.
Settle gate: uptime ≥ 4 min and 1-min load < 0.3 (the updaters stay resident when idle, so
counting their processes does not work). µs/cmd is taken over tally windows with > 2000 cmd/s,
which isolates the vkmark runs from idle desktop time. Evidence: `evidence/2026-09-10-ctx0/`.
