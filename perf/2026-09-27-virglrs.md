# Pin check: virglrs c76b2c7 → c3f6e4b

**Subject:** virglrs `c76b2c7..c3f6e4b`, four commits. Two of them are on paths the workloads take:
`c3f6e4b` (a venus ring that was rung while awake no longer parks inside the guest's notify
throttle, the fix for the seated replay stall in `spikes/venus-replay-stall-2026-09-27/`), and
`22bd712` (a draw with no pipeline of its kind bound is refused: every draw, dispatch and trace
now reaches the driver through `Driver::drawer`, which checks the command buffer's bindings). The other two are harness and test changes. libkrun is held at `60746d3e` on both arms. The
rows, the evidence and the driver are in `perf/virglrs-2026-09-27/`. Nothing went to
`perf/ledger.csv`.

## What this pass can and cannot see

The ring fix changes when a ring thread goes back to sleep. A ring that used to park and be rung
awake again now stays up for one more idle timeout, so its cost, if any, would show in the venus
throughput arms (vkmark, vk-replay, glmark2, gl-replay-venus). The draw check would show in the same
arms. The stall itself is too rare for five boots to catch, so its absence here says nothing about
the fix. The fix is verified by `loop.sh` (45/45 clean, against 2 stalls in 7 without it) and by
the full suite (151/151 on `c3f6e4b`).

**Display: 1280x800 at 59.97 Hz, scale 1.0, pinned in every guest** by `point.sh`, with
`perf-ledger.sh` checking the rate through `LIMINA_PERF_RATE=60`.

**The host was quiet.** The `gl-replay-llvmpipe` control stays within 729-744 at every point.

**No regression at this battery's resolution.** The arms overlap across the two pins throughout:

- gl-replay-venus is 46.3-47.2 on both pins.
- glmark2 is 2730-2762 on the baseline and 2745-2762 on the new pin.
- vk-replay's per-point medians are 1836/1799/1817/1833/1839, and n0's median is inside b1's

- Idle vkmark tracks time, not the pin. b0, n0 and b1 read 2619-2639, and n1 and b2 both read
  2691-2703. The bracket holds: n1 sits beside b2, and n0 sits between b0 and b1.
- The aquarium's range is the same on both pins (25k 44-51, 30k 38-43).
- Basemark's low-noise tests (geometry, canvas, SVG) agree within 1.1%. Shader pipeline spans
  1406-1609 on the baseline alone.

**The contended arm measures the boot, not the pin.** n0's 946/956 is the lowest pair, and the
aquarium beside it ran fastest (51 fps). This is the same inverse pairing the 09-24 and 09-26
passes recorded. The other new-pin boot reads 1377/1377, above every baseline boot.

**n0's Basemark produced no scores.** The suite never reached its result page on either attempt
(`REFUSING to report: run 2 yielded no scores either`). This is the harness stall recorded in
earlier passes, and it is not the ring stall: it hit b1 in the 09-26 pass without the fix and n0
here with it. The new pin therefore
has Basemark from n1 only, and n1 sits inside the b0-b2 range on every test.

## Against the 2026-09-26 pass

This pass's baseline, `c76b2c7`, is 09-26's new arm, on the same libkrun `60746d3e`, host mesa
`f3a220f`, vehicle and reboot pin. limina was `31042ea8` there and `0fcf5fc9` here. Between those
two, limina changed only its test harness, spikes, docs and the manifest pin.

| workload | 09-26 (all points) | here (all points) |
|---|---|---|
| gl-replay-llvmpipe | 729-747 | 729-744 |
| gl-replay-venus | 46.3-47.3 | 46.3-47.2 |
| glmark2-wayland-venus | 2536-2589 | 2730-2762 |
| vk-replay-venus-headless | 1771-1900 | 1741-1904 |

glmark2 reads about 7% higher here, and idle vkmark 7-9% higher, on both pins alike. For the
baseline this is the same `c76b2c7` build that read lower on 09-26. The control, gl-replay-venus
and vk-replay did not move. So the shift is in the day, not the tree. The host was rebooted
between the two passes, and this pass does not say which part of the day it was.
