# Pin check: virglrs 828a05b + libkrun 26450d76

**Subject:** virglrs `b900066..828a05b` + libkrun `32cc3776..26450d76`. The main change is the
VideoToolbox warm-up at renderer start (one VP9 session built and dropped on a thread of its own),
along with decode stats and the virglrs session's venus work (host-minted blob pages charged to
their context, maintenance6, no multisampling advertised without multisample array storage,
checked sampler/image slots). Rows, evidence and the driver: `perf/pin-2026-09-24/`; nothing went
to `perf/ledger.csv`.

## What this pass can and cannot see

No arm decodes video, so the warm-up can show only as startup cost, which no arm times. Its
effect is measured in `spikes/flush-latency/RESULTS.md`: a first play's longest queue wait drops
from 68-72 ms to 7.3 ms. What this pass checks is that nothing else moved on the venus and vrend
instruments.

**Display: 1280x800 at 59.81 Hz, scale 1.0, pinned in every guest.** `--display-resolution` fixes
only the size. The EDID carries the host screen's density and refresh, so on the built-in
ProMotion panel GNOME picks scale 1.333 at 120 Hz, and `perf-ledger.sh --verify` refuses the run.
`point.sh` therefore writes `monitors.xml` with `set-guest-display.py --write-config 1280x800 1.0
60`, reboots the guest, and verifies before measuring. `perf-ledger.sh` checks the rate as well,
through `LIMINA_PERF_RATE=60`. At 120 Hz the same tree read glmark2 and idle vkmark 3-5% lower.

**The host was quiet.** The `gl-replay-llvmpipe` control stays within 704-732 at every point.

**No regression at this battery's resolution.** Every arm overlaps across the pins. glmark2
(2399-2427) and idle vkmark (2278-2306) are the tightest the battery has read, and their ranges
coincide between the pins. Basemark's low-noise tests (geometry, canvas, SVG) agree to within 1.5%.

**The contended arm measures the boot, not the pin.** Its pairs cluster tightly within a boot and
spread 535-1161 across boots, with both pins at both ends: b0 1160 and n1 1136, against b1 548.
The aquarium beside it moves the other way (45-46 fps with the high pairs, 50 with the low), so
what varies between boots is how the GPU is shared between the two, not how much GPU there is.

**b0's Basemark produced no scores:** it stalled inside Shader Pipeline (`REFUSING to report:
run 2 yielded no scores either`). That is the harness stall recorded in earlier passes, on the
baseline tree.

## Against the 2026-09-23 pass

That pass also ran at 1280x800 and about 60 Hz, but its guests ran on a first boot. This pass
measures after the pin's reboot.

| workload | 09-23 (all points) | here (all points) |
|---|---|---|
| gl-replay-llvmpipe | 717-757 (quiet points; 370 at its worst) | 704-732 |
| gl-replay-venus | 45.2-46.6 | 45.5-46.3 |
| glmark2-wayland-venus | 2435-2528 | 2399-2427 |
| vk-replay-venus-headless | 1733-1920 | 1411-1783 |
| vkmark-default-venus | 1816-2384 | 2278-2306 |

vk-replay reads about 10% lower here (medians 1808 against 1629) and glmark2 about 3% lower, on
both pins alike. 09-23's newest point (virglrs `d57be22` + libkrun `32cc3776`) and this baseline
differ in the code (virglrs `d57be22..b900066`, six commits of decode stats and venus test gating;
limina `38f86033`, VA-API decode off the control thread) and in the vehicle: these guests were
measured after the pin's reboot, which relaunches the worker. Host mesa (`f3a220f`) and the vCPU
band policy (the same `[VCPU-RT]` dynamic band, one armed) are identical.

**The reboot likely costs vk-replay; it does not cost glmark2.** A second sweep held the tree at
the baseline pair and moved only how the pin is applied: `PIN=session` restarts the seated
session, so the first boot's worker is the one measured (`noreboot-legs.sh`, order s0 r0 s1,
enhanced guest only, limina `172d783d`; control 705-729).

| workload | s0 (session) | r0 (reboot) | s1 (session) |
|---|---|---|---|
| vk-replay-venus-headless | 1747 1728 1860 | 1604 1710 1765 | 1894 1901 1613 |
| glmark2-wayland-venus | 2419 2414 2424 | 2403 2391 2424 | 2413 2414 2428 |
| vkmark-default-venus | 2287 2291 2181 | 2284 2295 2282 | 2286 2289 2293 |
| vkmark under aquarium 25k | 392 480 | 1133 1161 | 713 773 |

The session arm's six vk-replay runs have a median of 1803, 09-23's level; the six reboot boots
(five above, r0) have per-boot medians of 1598-1770. Two session boots do not clear the
instrument's floor (one 9-15% low outlier per set, s1's 1613 among them), so this is a lean, not a
verdict. glmark2 and idle vkmark do not move with the vehicle, so glmark2's 3% against 09-23 is in
the code or the day. Whatever the answer, **a sweep that compares against first-boot numbers pins
with `PIN=session`.** This sits on top of the regression still open from 09-17 to 09-21, and is
not it.

## Vehicle

Debug worker with the dev `opt-level = 3` overrides, built per point by `point.sh`; EFI+venus
(`boot-enhanced-efi-kk.sh`), 4 vCPU / 4 GiB, `--display-resolution 1280x800`, and the guest display
pinned as above (`evidence/*/pin-*.txt`). Enhanced image `Fedora-Workstation-44.enhanced.raw`, stock
`Fedora-Workstation-44.stock.test.raw`; Basemark harness frozen at virglrs `d0416c9`. Host on AC
power. No watchdog (poisoned-context) marker at any point.
